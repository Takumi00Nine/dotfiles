Stage 1 のスコープは**セッション族(新規/閉じる/切替)を除く全機能**（マイク・Enter・YouTube制御・ダイヤル・コンボ）。

## 1. Launcher 設定手順（ユーザー作業）

有線接続で Launcher (https://launcher.keychron.com/) を開き、各ボタンを以下の通り設定する。
**04・03・ダイヤル単体・Round は既存のまま(左クリック・右クリック・スクロール・BT切替用)で変更不要。**

### 1-1. 応用機能(hold-tap)でタップ/ホールドを別キーに割り当てる

| 物理ボタン | Launcher: タップ側出力 | Launcher: ホールド側出力 |
|---|---|---|
| 01 | `KC_F13` | `KC_F14` |
| 02 | `KC_F15` | `KC_F16` |
| M1 | `KC_F18` (**既存の割当のまま変更しない**) | `KC_F19` |
| M2 | `KC_ENTER` (実キーEnter。中立コードではない) | `KC_F20` |

手順: 各ボタンで「応用機能」→ タップ側/ホールド側それぞれに上表のキーを設定 → 保存。
**M1のタップ側は今まで通り`KC_F18`のままでよい**（変更禁止。既存物理ボタンとの移行を安全にするための意図的な再利用。詳細は下記「設計判断1」）。

### 1-2. 確認（Reload Config 前でもLauncher側だけで確認可）
- 01/02/M1 を軽くタップ → 各ボタンの反応が単発であること。
- 01/02/M1/M2 を長押し → ホールド側のキーがリピートして送られること(市販キーボードチェッカー等で確認可)。

### 1-3. Hammerspoon側の反映
1. `~/work/dotfiles` で `./install.sh` を実行（`hammerspoon/nape_pro/` ディレクトリが `~/.hammerspoon/nape_pro` へシンボリックリンクされる）。
2. Hammerspoon メニューバー(🔨) → **Reload Config**。
3. 何か問題があれば画面右上に `hs.alert` でエラーメッセージが出る(nape_pro読み込み失敗時など)。**その場合もF17/F18(旧)は動作し続ける**(フォールバック設計・後述)。

## 2. 設計判断と根拠（実装者の判断・要リーダー確認）

### 設計判断1: 中立キーコード表 と F17/F18 の扱い
**選定: F13/F14/F15/F16/F19/F20を新規使用。F18はM1タップとして「その場で再利用」、F17は変更せず放置。**

根拠:
- macOS/Hammerspoonが安全に使えるfunctionキーは F13〜F20 の8個のみ(F21〜F24はCarbon HIToolboxのkVK_*に存在せず、Hammerspoonの`hs.keycodes.map`もF1〜F20までしか定義していないことをWeb一次情報で確認)。
- Stage1で必要な中立コードは 01T/01H/02T/02H/M1H/M2H の6個 + (検討の結果不要と判断した)M2T。F17/F18を除外すると6枠しか残らずギリギリ足りるが、F18は「そのまま新M1タップ(マイクトグルの後継)として使う」方が移行として自然かつコード領域を圧迫しない。
- F18の**ハンドラの中身**は拡張する(cmux activate+リーダーペインfocusを追加)が、**入出力の意味(タップ→マイクトグル)は完全に後方互換**。旧物理ボタンがF18を送り続ける限り、押した時の見た目の挙動は「マイクトグル」のまま変わらない(強化版になるだけ)。
- F17は今回どのボタンにも新規に割り当てない設計(M2タップは下記の理由で実Enterに変更)。**削除はせず放置**(旧物理ボタンが今もF17を送っているかもしれないため。使われなくなったことが確認できたら次回整理で削除候補)。
- nape_pro モジュールの読み込み・setup()に失敗しても、F17/F18のhs.hotkey.bind自体は**必ず登録される**ようinit.lua側でpcall境界を分離した。F18は更にnape_pro読み込み失敗時に**旧ロジックへ自動フォールバック**する(コード上は`hammerspoon/init.lua`の一箇所に旧関数を残置)。

### 設計判断2: M2=Enter の実装方式
**選定: (a) デバイスから実Enterキーを送り、Hammerspoonは一切介入しない。**

根拠:
- Enterは最頻・最重要操作。(b)「中立コード→Hammerspoonで変換」だと、Hammerspoonがクラッシュ/未起動の間はEnterが一切送れなくなる(致命的)。(a)なら物理的に本物のEnterキーイベントがOSに直接届くので、**Hammerspoonの生死に一切依存しない**。
- 遅延: (a)はHammerspoonのイベントループを経由しないため理論上(b)よりむしろ低遅延(既存F17実装の`keyStroke`と比べても、こちらはHammerspoon側のディスパッチが完全に無い)。
- コンボ(02+M2)の検出は「M2のホールドコード(F20)」を見るので、M2タップ(実Enter)は一切combo判定に関与しない。→ 「combo検出のためにHammerspoonがEnterキーイベントを監視する」必要すらなく、実装がシンプルになった(タップ経路とhold経路が完全に独立)。
- リスク/フォールバック: Launcherの応用機能(hold-tap)のタップ側スロットに`KC_ENTER`を割り当てられない実装だった場合(要実機確認)は、代替案としてタップ側を`KC_F17`にし、`hammerspoon/init.lua`のF17ハンドラ(既存のままEnter送出)をそのまま使う「Plan B」に切り替え可能(コード変更不要、Launcher設定を戻すだけ)。人間チェック台本の項目2-2で確認すること。

### 設計判断3: コンボ検出方式・閾値
**選定: 「両ボタンのホールドコードが同時に流れている状態」で結成・「短押しはrelease時に発火、長押しは閾値を超えた瞬間(押しっぱなしのまま)に発火」。**

根拠:
- タップコードは一切combo判定に使わない → **単押しの遅延は常にゼロ**(検出方式の選択が単押しの体感に影響しない設計)。
- コンボは「双方をやや押し込む(hold状態にする)」操作になるため、うっかり誤発火しにくい(=対角禁止・隣接ペアのみという設計原則とも整合)。
- 長押しは「閾値を超えた瞬間に確定発火」(離すのを待たない)。理由: 「破壊的操作ほど押す時間が長い」という設計原則上、閾値を超えた時点で既に「長押しの意思確認」は完了しているとみなせる。離すまで待つと、Ctrl+Cのような割り込み系アクションの体感レスポンスが悪化する。
- 短押し/長押し境界 = `M.CONFIG.comboLongMs`(既定600ms)。`hammerspoon/nape_pro/init.lua`の`M.CONFIG.comboLongMs`を書き換えてReload Configすれば即調整可能。
- 実装上の注意(既知の制約): 長押し確定のタイミングはOSのキーリピート("システム設定→キーボード→キーリピート/リピート入力認識までの時間")に依存する(デバイスのホールドコードのオートリピートをHammerspoon側の"tick"として利用しているため)。リピート認識までの時間を極端に長く設定していると、長押し確定が体感で遅れる場合がある(離した瞬間には必ず遅れなく確定するので機能自体は壊れない)。

### 設計判断4: AI窓口(M1+M2短押し)の「全消し⇄復元」実現方法
**選定: Ctrl+E(行末へ)→Ctrl+U(行頭までkill、readlineのkill-ringに積まれる)。復元はCtrl+Y(yank)。クリップボードは使わない。**

根拠(Web一次情報で裏取り済み・absolute-rules #4準拠):
- Claude Code CLIはreadline系のキーバインドを踏襲しており、Ctrl+A/E(行頭/行末移動)・Ctrl+U(行頭までkill)・Ctrl+K(行末までkill)・**Ctrl+Y(yankでkill-ringから復元)**が確認できた(公式ドキュメント・複数の解説記事で一致)。
- クリップボード経由の代替案は「ユーザーが今コピーしている内容を上書きしてしまう」という副作用が非常に重い(タスクの指示にある「保守的に」という要求に反する)ため不採用。kill-ring方式はシステムクリップボードに一切触れない。
- 5秒以内の再押しで復元、という判定は**Hammerspoon側の状態(`logic.newAiInputToggle`)のみで管理**し、Claude Code側の内部状態を読み取る必要が無い(タスクの「TUIのテキストを読めない制約下で」という前提を満たす)。
- **既知の制約(未解決・要人間チェック)**: 複数行入力(Shift+Enterで改行した状態)の場合、Ctrl+E/Ctrl+Uは「カーソルのある行」にしか効かない可能性がある(readline標準は行単位、Claude Code独自TUIの実装次第)。単一行入力では確実に動作する設計だが、複数行入力での完全な全消しは未検証。人間チェック台本の項目6-3で確認し、問題があれば「Ctrl+E→Ctrl+Uを複数回連打する」等の追加対策をリーダーに相談する。

### 設計判断5: cmux/YouTubeの場所判定と移動
**選定:**
- **cmuxにいるか否か**: `hs.application.frontmostApplication():bundleID() == "com.cmuxterm.app"`。
- **リーダーペイン特定**: `cmux current-workspace` → `cmux list-panes --workspace <ref>` の出力をパースし、`[dock:global]`タグの付いたペインを除外して最小番号の`pane:N`を採用(Knowledge/cmux-cli-reference.mdのヒューリスティックをそのまま採用)。**2026-08-05に実機で読み取り専用コマンドを実行し、出力フォーマット(`* pane:1  [2 surfaces]  [focused]` 等)を実測確認済み**(このタスク自身のcmuxセッションで検証。テストにも同じ実測フォーマットを使用)。
- **特定失敗時のフォールバック**: パース結果が空、または`cmux`コマンド自体が失敗した場合は`cmux focus-pane`を呼ばず、`activate()`(cmuxを前面化するだけ)に留める。例外は握りつぶし、他の処理を止めない。
- **YouTube側の移動・ホーム遷移・URL記憶**: 既存資産(mic-video-toggle)と同じAppleScript+JS実行の作法を踏襲。「アクティブタブがyoutube.comかどうか」を見て01/02タップは対象を絞り込み、02+M2橋コンボは「Chrome全体からyoutube.comタブを探す→無ければ新規タブでホームを開く」という広めの探索を行う(用途が違うため意図的に絞り込み方を分けている)。

## 4. 既知の制約・未解決点

1. **Launcherのhold-tapタップ側にKC_ENTERを割り当てられるかは実機未確認**(設計判断2のPlan B参照。ダメだった場合はF17を使うPlan Bへ切替可能・コード変更不要)。
2. **リーダーペイン特定ヒューリスティックは単一ケースの実測のみ**(dock:global除く最小pane番号)。claude-teams等でリーダー以外に複数の実ペインが並ぶ状況(例: チームメイト複数人)での検証は未実施。誤ったペインへフォーカスする可能性はゼロではない(その場合も「cmuxをアクティブ化する」以上の実害は無い設計)。
3. **AI窓口の全消しは複数行入力での完全性が未検証**(設計判断4)。
4. **ダイヤルの回転方向(delta符号)とシーク/選択の対応が実機で正しいかは未検証**(`seekInvert`/`selectInvert`で調整可能な設計にして吸収)。
5. **3ボタン以上の同時押し(例: 01+M1+M2)の挙動は未定義**(最初に成立したペアだけがコンボとして扱われ、3つ目のボタンは単に無視される。事故率は低いと判断し対応を見送った)。
6. **OSのキーリピート設定(遅延・速度)が極端な値だと、長押し確定タイミングの体感が変わる**(設計判断3)。
7. 実機でのHammerspoon Reload Config・Launcher実機検証は本ワーカーでは実施していない(理由: 稼働中の実環境グローバルイベントタップを不用意に有効化しないための安全側判断)。**人間チェック(本ドキュメント第3節)が初回の実地検証を兼ねる**。
8. **cmux CLI呼び出し(`hs.execute`)は同期・タイムアウト無し**(2026-08-05 Codexレビュー指摘)。cmux側が万一ハングすると、その間Hammerspoon全体のイベント処理(このキーマップ以外のホットキーも含む)が止まる。実測では読み取り系コマンドは即座に返ることを確認済みだが、恒久対策(`hs.task`化)はStage 1では見送った。長時間反応が無い(マウスの他ボタンも効かない)場合はHammerspoonの再起動が必要になる可能性がある。
